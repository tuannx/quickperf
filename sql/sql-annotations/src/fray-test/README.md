# Fray controlled-concurrency tests (opt-in)

This directory contains [Fray](https://github.com/cmu-pasta/fray) tests for the SQL
recording path. Fray controls the thread scheduler and explores interleavings
systematically instead of relying on lucky timing.

The tests target the state that is written on the threads executing the SQL queries
of the code under test (datasource-proxy invokes
`DataSourceQuickPerfListener.afterQuery` on those threads):

| Test | Component under test |
| --- | --- |
| `org.quickperf.sql.repository.SqlRecordingConcurrencyFrayTest` | `SqlMemoryRepository` / `SqlExecutions` (`java.util.ArrayDeque`) |
| `org.quickperf.sql.SqlRecorderRegistryConcurrencyFrayTest` | `SqlRecorderRegistry` in the dedicated-JVM mode (`java.util.HashMap`) |
| `org.quickperf.sql.DataSourceProxyVerifierConcurrencyFrayTest` | `DataSourceProxyVerifier` (unsynchronized check-then-act) |

## Build wiring

The tests are **not** part of the default build. The `fray` profile in
`sql/sql-annotations/pom.xml` (activate with `-Pfray`) adds this source root as a
test source root and adds the `fray-junit` dependency.

## Running

Fray 0.9.2 needs a JDK 25 that it instruments itself (with its Gradle plugin this
happens automatically; with Maven, prepare it once, following the same recipe the
plugin uses):

```sh
# 1. Build an instrumented JDK 25 with jlink and the Fray JDK instrumentation agent
$JDK25/bin/jlink -J-javaagent:fray-instrumentation-jdk-0.9.2.jar \
    -J--add-modules=org.pastalab.fray.instrumentation.jdk --fray-instrumentation \
    --add-modules java.se --output fray-java
# (the exact jlink invocation is generated by org.pastalab.fray.gradle's
#  FrayWorkspaceInitializer; the JVMTI agent ships in fray-jvmti-<os>-0.9.2.jar)

# 2. Compile the module and the tests, then run with the instrumented JDK
mvn -Pfray -pl sql/sql-annotations test-compile
fray-java/bin/java \
  -agentpath:<extracted libjvmti.so> \
  -javaagent:fray-instrumentation-agent-0.9.2.jar \
  --add-opens java.base/java.lang=ALL-UNNAMED \
  --add-opens java.base/java.util.concurrent.atomic=ALL-UNNAMED \
  --add-opens java.base/java.util=ALL-UNNAMED \
  --add-opens java.base/java.io=ALL-UNNAMED \
  --add-opens java.base/sun.nio.ch=ALL-UNNAMED \
  --add-opens java.base/java.lang.reflect=ALL-UNNAMED \
  -Dfray.organize.by.test=true -Dfray.workDir=<report-dir> \
  -cp <test classpath> org.junit.platform.console.ConsoleLauncher execute \
  --select-class org.quickperf.sql.repository.SqlRecordingConcurrencyFrayTest
```

## First results (2026-11-02, fork)

Measured with the recipe above (Fray 0.9.2, instrumented Corretto 25):

* Fray alone does **not** expose these races: the faulty windows are plain-memory
  accesses with no synchronization point inside, so Fray's controlled scheduler has
  nothing to interleave there (recording: 1,000 iterations / 165 covered timelines,
  pass; registry: 200 / 11, pass; verifier: 1,000 / 18, pass).
* A plain-JVM stress of the same scenarios does expose them on the current code:
  concurrent recording loses statements in 6/6 rounds (only 3,438–122,197 of
  400,000 statements recorded; one `ArrayIndexOutOfBoundsException` inside
  `ArrayDeque.grow`), registry iteration throws
  `ConcurrentModificationException` almost immediately, and the verifier misses
  the two-proxies situation in 2/200,000 rounds. The same stresses pass on
  variants using `ConcurrentLinkedDeque`, `ConcurrentHashMap` and a synchronized
  verifier, which validates that the harnesses discriminate.
* The Fray tests are kept as the systematic harness for these components: their
  assertions encode the invariants, and they do catch regressions as soon as an
  interleaving becomes reachable through a synchronization point (the fixed
  `SqlExecutions` variant, whose `ConcurrentLinkedDeque` operations are visible
  to Fray, covers 1,000/1,000 timelines).
